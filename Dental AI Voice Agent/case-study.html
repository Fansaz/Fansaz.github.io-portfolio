01 — The problem

The bottleneck was answering the phone

A dental surgery practice was answering only 45% of its inbound calls. Its lead flow is driven by paid marketing, so every unanswered call is a lost high-value surgical case.

The constraint sat specifically on inbound call capacity, not on lead generation. The practice could not scale marketing spend any further, because leads were already being lost before anyone could service them. They estimated the gap at roughly $730,000 a year.

Scope was deliberately narrow

The line only handles four services: wisdom teeth, dental implants, dentures, and emergency extractions. Anything else — routine cleanings, whitening, orthodontics, checkups — had to be politely declined rather than booked.

The practice also wanted the three higher-value services prioritized over emergency extractions under scheduling pressure. That business rule had to be implemented without ever compromising medical urgency, which shaped the whole safety model.

Why a middleware layer exists

This was the central design decision. Voice-platform tools make one HTTP call each. But booking in the CRM needs two sequential calls with a data dependency: the contact upsert returns a contactId, and the appointment call requires it.

That left two options. Either the language model orchestrates three separate tool calls and correctly carries an ID between them mid-conversation, or the sequencing lives in code. I put it in code. The Worker exposes one clean booking endpoint; contact lookup, calendar mapping, retries and error classification all happen server-side where they are deterministic and testable.

A second benefit fell out of that choice: the CRM API token never touches the voice platform at all. It lives only in encrypted secret storage on the Worker.

03 — Build

End to end, in eight phases

Each phase is sequenced because the next one depends on it: the agent needs a prompt before it needs tools, and tools need a backend before they need a phone number.

01

Agent design and prompt engineering

The agent persona is defined by a structured system prompt with explicitly separated concerns, so that behavioural rules can be changed without disturbing safety rules.

  • Call flow — a master five-step procedure that is the single source of truth for sequencing
  • Non-negotiable boundaries — never diagnose, never promise pricing or outcomes, never advise on medication
  • Red-flag screening — three consolidated safety questions and the 911 escalation path
  • Business prioritization — revenue-based slot preference, written as explicitly subordinate to safety
  • Forbidden statements — literal phrases that constitute an audit failure
  • Tone — brevity limits, one question at a time, no internal jargon spoken aloud
02

Model selection

Gemini 2.5 Flash Lite, chosen for three specific reasons: roughly 3× cheaper per token than comparable alternatives, on the voice platform's HIPAA-eligible model list so a future production migration does not require re-validation, and not a reasoning model — which mattered more than expected, as problem 01 below explains.

03

Knowledge base

Deliberately lean: clinic hours, location, FAQs, and per-service price estimates. This was a reversal. An earlier iteration ran a 13-document knowledge base, which made the agent recite source text almost verbatim and blend entries into long, robotic answers. Rules that must always apply moved into the always-in-context system prompt; only genuine reference material stayed behind.

04

The middleware

A Cloudflare Worker with two public endpoints and one authenticated admin endpoint.

  • Auth — shared-secret header on every endpoint except the health check. Voice-platform tool calls carry no cryptographic signature, so a shared secret is the available control
  • Service mapping — done in code, so the agent only ever handles semantic names like WISDOM_TEETH, never raw calendar IDs
  • Timezone — day boundaries computed against Eastern midnight, not UTC midnight, with the DST offset derived dynamically rather than hardcoded
  • Retries — transient failures retry twice before the caller hears anything; genuine conflicts skip retries entirely
  • Failure log — every failure written to Cloudflare KV with the real upstream error, 30-day retention
05

CRM and calendar integration

Authenticated with a Private Integration Token scoped to a single sub-account — the modern alternative to a full OAuth marketplace app, with no review process or redirect flow. Scopes were granted least-privilege: read calendars, write calendar events, read and write contacts.

One calendar per service, each with its own duration and business hours, because the CRM's model is strictly one calendar per service. The whole integration was built and validated against a free developer sandbox, so no real client data was touched during development.

06

Tool wiring

Two webhook tools, each with a JSON-schema body where every parameter carries a description the model reads at runtime to decide what to send. The shared secret is stored as a secret-type header rather than plaintext config.

  • check_availability — appointment type (enum of the four services), start date, end date, timezone
  • book_appointment — appointment type, full name, phone, exact start time
07

Telephony and human transfer

A toll-free number with voice capability, imported via the native Twilio integration and assigned to the agent, with SHAKEN/STIR registered to improve answer rates on the outbound transfer leg.

Transfer uses a system tool with a natural-language trigger condition and a fixed destination number, as a conference transfer so the caller and the human end up connected and the agent drops out. The destination can be any phone number — it does not need to be connected to the voice platform at all.

08

Post-booking automation

A CRM workflow triggered on appointment status “new”, filtered to API-created appointments: confirmation SMS immediately, a wait-until step timed to one day before the appointment, then a reminder SMS.

The trigger choice mattered. The CRM's “customer booked appointment” trigger only fires for bookings made through its own booking widget. Appointments created through the API need the appointment-status trigger, which explicitly supports API-sourced events.

04 — Debugging

Six problems worth reading about

Each of these was found by testing, diagnosed from evidence rather than guesswork, and fixed at the root rather than patched at the surface.

PROBLEM 01

The agent read its own internal reasoning out loud

Symptom
The agent spoke its entire chain of thought before answering: “The user is asking about working hours. I should answer concisely as this is a phone call. I should not use digits…” — and then gave the actual answer.
Cause
The configured model was a reasoning model that emits chain of thought inline in its response. Suppressing it requires a vendor-specific API parameter, and the platform's custom-LLM integration passes responses through verbatim — it has no provider-specific logic to strip another vendor's reasoning format. The platform's own “reasoning effort” control sends a generic parameter that this provider silently ignored.
Fix
Switched to a natively integrated model where the platform actually controls the reasoning setting. This also resolved a compliance problem: the original model was not on the HIPAA-eligible list, and a custom-LLM endpoint routes conversation content to a third party outside the platform's BAA boundary entirely.
Takeaway“Supports any OpenAI-compatible endpoint” does not mean every platform feature works with every endpoint.
PROBLEM 02

Every booking failed as “that time just became unavailable”

Symptom
The agent offered times, the caller accepted, and every single booking attempt was rejected as already taken — on an empty calendar.
Diagnosis
Added temporary request-body logging to the Worker and captured the real tool call: 
{"appointmentType": "NP-COMP", "fullName": "",
 "phone": "", "startTime": "2026-07-10T12:15:00-04:00"}
Two things were wrong. The appointment type was a stale enum value from a previous iteration — not a key in the calendar map, so no calendar could be resolved — and the name and phone fields were empty. The enum values in the tool definition had never actually saved; only the description text had been updated. The model was constrained to choosing from obsolete options.
Second cause
The Worker was classifying any HTTP 400 as “slot unavailable”, which disguised the real failure as a scheduling conflict. That mislabeling is what made the bug so hard to see.
Fix
Corrected the enum values, and rewrote error handling to read what the upstream API actually says — see problem 06.
PROBLEM 03

The agent sounded robotic and over-explained everything

Symptom
Long, formal, hedge-laden answers. It often merged two unrelated knowledge-base entries into a single response.
Cause
The knowledge base was written as formal reference documents with complete, fully-qualified paragraph answers, and the model was reciting them nearly verbatim. More content made it worse, not better.
Fix
Layered:
  • Rewrote knowledge-base entries as short, conversational answers
  • Added a hard two-sentence default limit, with explicit exceptions for safety screening and final confirmations
  • Added a rule that when a question touches two knowledge-base topics, the agent answers from one and never blends
  • Moved behavioural rules out of the knowledge base and into the system prompt entirely
Also caught hereA teammate had added two runtime guardrails to suppress over-explaining. Their retry-feedback messages said “I am not sure I understand your question” — a non-sequitur when the actual violation is answering too much. Had they fired, they would have made the agent sound more broken, not less. Removed in favour of fixing the root cause.
PROBLEM 04

The agent re-asked a question it had already answered

Symptom
Caller says “I have pain in my front tooth and I think it needs extraction.” The agent completes safety screening, then asks: “Is this for a wisdom tooth, a dental implant, or a denture issue?”
First attempt
Added a prose instruction telling it not to re-ask. It did not hold.
Real cause
The flow logic was scattered across three separate prompt sections written far apart. Following it required the model to connect instructions across distant blocks and hold state across a multi-turn sub-dialogue. That is a weak mechanism.
Fix
Consolidated the entire call sequence into a single explicit, ordered procedure at the top of the prompt, with the never-repeat rule stated at the exact transition point where the failure occurred. Also broadened the classification rule: any request to extract a non-wisdom tooth is an emergency extraction, whether or not the caller uses the word “emergency” — because that is the only extraction service offered.
TakeawayWhen a model repeatedly fails to follow an instruction, restructure the instruction. Do not just restate it more emphatically.
PROBLEM 05

Timezone and “today” were not grounded

Symptom
Intermittent availability lookups against the wrong day, and times quoted without any timezone reference.
Cause
Two distinct bugs. The agent had no reliable notion of the current date — it was inferring “today” rather than knowing it. Separately, day boundaries in the Worker were computed at UTC midnight while the practice operates on Eastern time.
Fix
Injected the platform's real-time UTC variable into the prompt as an explicit source of truth, and computed Eastern midnight properly in the Worker with the offset derived dynamically so it stays correct across daylight-saving transitions. Added a requirement that the agent states the timezone out loud when first offering times, so an out-of-state caller is never ambiguous about what “3:30” means.
PROBLEM 06

Error handling that hid the truth

Symptom
Validation errors, rate limits and transient failures all surfaced to the caller as a phantom scheduling conflict, because the Worker treated any 400 or 409 from the booking API as “slot taken”.
Fix 1 — honest classification
Only report a conflict if the upstream error actually indicates one. Verified by deliberately double-booking a slot to capture the real message: 
{"message": "The slot you have selected is no longer available.",
 "error": "Bad Request", "statusCode": 400}
Fix 2 — retries
Non-conflict failures retry twice before surfacing; genuine conflicts skip retries, since retrying cannot free a taken slot. Verified: a real conflict still fails in under a second rather than stalling through pointless retries. 
// Transient failures self-heal silently;
// genuine conflicts are never retried.
for (let attempt = 0; attempt <= retries; attempt++) {
  result = await ghlFetch(env, path, options);
  if (result.ok) return result;
  if (skipRetryIf && skipRetryIf(result)) return result;
  if (attempt < retries) await delay(delayMs);
}
Fix 3 — persistent log
Every failure is written to Cloudflare KV with the real upstream error, 30-day retention, queryable through an authenticated endpoint. Previously, diagnosing a failure meant already watching a live log stream at the exact moment it happened. Now every failure leaves a permanent record.
05 — Safety

Designed safety, not incidental safety

This is a healthcare-adjacent product, so the safety model is explicit and takes precedence over every commercial rule in the system.

Three-question red-flag screening

Asked one at a time, consolidated down from an original seven so a distressed caller does not sit through an interrogation — while still covering every original clinical signal.

  • Trouble breathing or swallowing, or signs of a severe allergic reaction
  • Heavy bleeding that will not stop, or swelling spreading toward the eye, jaw or neck
  • Major facial or head injury, loss of consciousness, confusion, chest pain, or stroke-like symptoms

Any “yes” instructs the caller to call 911 or go to an emergency department, and stops all scheduling.

Emergency state is sticky

An early test exposed a serious flaw: after correctly flagging an emergency, the caller said something unrelated and the agent went straight back to normal booking. Fixed with an explicit rule that an emergency flag persists for the remainder of the call, regardless of what the caller says next.

Business rules can never override safety

The revenue-prioritization rule is written to be explicitly subordinate. It applies to slot preference only, and never to an actual medical emergency. Alongside it sit hard behavioural limits — no diagnosis, no treatment recommendations, no medication advice, no guaranteed pricing or outcomes — plus an explicit list of forbidden phrases that count as audit failures.

Compliance position, stated plainly

This build is not HIPAA-covered. A BAA and zero-retention mode require an enterprise agreement, and a CRM sandbox is not a compliant environment. All testing used synthetic patient data. The model was chosen to be HIPAA-eligible specifically so that a future production migration does not require re-validating the agent on a different model.
