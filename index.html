5

Ava, AI voice receptionistMF-01 VOX · dental surgery practice, client anonymized

Status. Working end to end on a real phone line. Sandbox CRM, synthetic patient data.

5.1Overview

Answers a dental surgery practice's inbound calls, screens callers for medical emergencies, books qualified callers onto the live practice calendar, and hands off to a person on request. Before the build the practice answered 45% of its calls.

A small Cloudflare Worker sits between the voice platform and the CRM. Booking needs two dependent API calls, which a voice tool cannot chain reliably, and the CRM token should never live in the voice platform's config. The Worker does the sequencing, retries and error classification where it can be tested.

  • ElevenLabs Agents
  • Gemini 2.5 Flash Lite
  • Cloudflare Workers + KV
  • GoHighLevel API v2
  • Twilio

5.4Errata

  1. E1

    The agent read its own reasoning aloud

    Cause. The model emitted its chain of thought inline, and the platform passes custom model output through untouched.

    Fix. Moved to a natively integrated model the platform controls, which is also on the HIPAA-eligible list.

  2. E2

    Every booking failed as "slot unavailable"

    Cause. The tool's enum values had never saved, so the agent sent a stale service key, and the Worker labelled every HTTP 400 a conflict.

    Fix. Corrected the enum, then classified errors by what the upstream message actually says.

  3. E3

    Asked for a service the caller had already named

    Cause. Call flow rules were spread across three distant prompt sections.

    Fix. One ordered call flow at the top of the prompt, with the "never ask again" rule placed at the exact step where it failed.

  4. E4

    An emergency flag did not stick

    Cause. After a red flag, an unrelated reply sent the agent back to booking.

    Fix. The emergency state now persists for the rest of the call, and business rules are written as subordinate to safety.

ColdOutbounderMF-02 OUT · autonomous cold email for dental practices

Status. Running unattended on a VPS. Figures read from the live system on 5 Oct 2026.

6.1Overview

A two-person agency needed outbound that runs without anyone watching it. The system finds independent dental practices, writes personalised sequences, sends from six warmed mailboxes, classifies every reply, and routes genuine interest into the CRM while suppressing anyone who asks to be left alone.

A Postgres state machine is the spine. Instantly knows what it sent; Postgres knows what that meant and what happens next. A reconciler reads Instantly's records every ten minutes and repairs any drift, so the two never disagree silently.

  • PostgreSQL 17
  • Python 3.13
  • Docker + s6
  • Instantly API v2
  • Apollo
  • GoHighLevel v2
  • FastAPI

6.4Errata

  1. E1

    842 leads frozen since upload

    Cause. The campaign lookup only matched keys ending in varA or varB; live keys ended in a date, so their leads never left the queue while Instantly emailed them for weeks.

    Fix. Fixed the match, backfilled 536 records, and added the reconciler so state repairs itself.

  2. E2

    "Not interested" read as a buying signal

    Cause. The classifier's pattern for interested also matches inside the refusal.

    Fix. Explicit precedence, refusal tested before interest, and 43 tests pinning both directions.

  3. E3

    Every reply silently discarded

    Cause. Replies were matched to leads by the To address, which on a reply is our own mailbox.

    Fix. Found by checking a real opt-out instead of trusting a green cron status.

  4. E4

    Opt-outs recorded, then ignored

    Cause. The suppression table had one INSERT and no SELECT anywhere, and the stop call pointed at an endpoint that returns 404.

    Fix. Uploads now read the list, and stopping uses a blocklist entry verified to work.

  5. E5

    One email in eight named the wrong business

    Cause. The lead source had attached contacts to companies they did not work for.

    Fix. A corroboration check on email domain against company name, with a generic phrase when it fails.

Harbor & Pine DM setterMF-03 DMS · AI setter that books its own appointments

Status. Live end to end. Harbor & Pine is a fictional agency; every lead and booking is mock data.

7.1Overview

A lead sends a DM. The setter qualifies them against a five-document knowledge base, offers live calendar slots, and books the consultation while the CRM fills in beside the conversation.

The brief said the agent was already connected to a CRM and a database. A read-only audit found the integrations had never been saved, the CRM token could not create appointments, the database had zero tables, nothing could reach the agent over HTTPS, and a previous bot was still live. Rather than patch five problems in someone else's CRM, the CRM itself was built in Postgres.

7.4Errata

  1. E1

    Replies took about nine seconds

    Cause. Spawning the agent CLI cost 2.8 s before inference, and the agent loop inflated a 1,700-token prompt to 30k to 47k tokens.

    Fix. A direct structured model call per reply, 2.6 times faster, with the same persona files.

  2. E2

    Double booking depended on the model remembering

    Cause. Four calendars with their own hosts, buffers, notice windows and closures.

    Fix. A Postgres function materialises every legal slot; booking flips one, and a unique constraint makes double booking impossible.

  3. E3

    Exact prices missed by vector search

    Cause. "Is it really $2,997?" matches a string, not a concept.

    Fix. Vector results fused with Postgres full-text ranking.

Funnel StudioMF-04 FUN · AI funnel builder for a live event

Status. Load-tested with 100 scripted guests. Primary and identical backup deployments.

8.1Overview

Guests at a live event scan a QR code, answer four questions in a chat, and leave with their own landing page. It had to hold more than 100 people at once on one venue Wi-Fi, each in a private workspace, with no accounts.

The agent has file tools and internet access, so isolation is enforced in code: a plugin in front of every tool call pins each guest to their own folder, allows only the tools the job needs, and blocks the call if its check times out. A second server runs an identical copy as the event's spare.

8.4Errata

  1. E1

    32 of 100 guests turned away

    Cause. Joining was capped at 12 a minute per connection and the line held 60 messages, while the CPU peaked at 52%.

    Fix. 200 joins a minute and a 300-message line. Nobody has been turned away since.

  2. E2

    A three-second answer waited six minutes

    Cause. Quick chat replies queued behind minute-long page builds.

    Fix. Intake messages got their own lane; reply time fell from 6.2 min to 46 s.

  3. E3

    The first fast lane backfired

    Cause. Promoting anything that waited four minutes promoted everything at peak, and the worst reply took 14 minutes.

    Fix. Removed the promotion rule. The repeatable test harness is what caught it.

  4. E4

    The backup could have deployed over the live site

    Cause. The deploy script trusted a cached site id before looking the site up by name.

    Fix. Only the token was copied, and cached ids are now ignored unless the name matches.

Reschedule guardrails for a live booking agentMF-05 RSV · client work, anonymized

Status. Built and validated against the client's live scheduling system.

9.1Overview

An SMS booking agent for a multi-location auto service business qualified leads and booked them into the shop's scheduling system, but it could only create appointments. The client asked for rescheduling: deposits are non-refundable, but a booking can move.

The feature was small. The guardrails were the job. The agent must never touch an appointment a person booked, and must never cancel without a confirmed replacement. Both are enforced by how the code finds and orders its work, not by instructions to the model.

  • Hermes agent + booking skill
  • GoHighLevel conversations
  • Supabase
  • ShopMonkey API v3

9.2Electrical characteristics

ParameterConditionsTypUnit

9.3Signal chain

  1. Customer SMS"can't make my slot"
  2. Agentstates policy, offers openings
  3. Bookings tableonly bookings the agent made
  4. New slotcreated and confirmed first
  5. Old slotreleased only after success
  • No booking on record: nothing is touched, the team is told
  • Release fails: new booking kept, team alerted to clean up

9.4Guardrails

  1. G1

    Only touch what the agent booked

    The old appointment id is read only from the agent's own bookings table, never from a search of the shop's calendar, so a human booking cannot be reached at all.

  2. G2

    Never leave a customer with nothing

    Create the new appointment, confirm it, then release the old one. If the new booking fails the old one is untouched; if the release fails the customer keeps the new one and the team is alerted.

  3. G3

    Carry the deposit

    The existing booking code consumed a deposit on every booking, so a naive rebook would have demanded a second one. A move reuses the original.

  4. G4

    Live skill untouched until approved

    Built in a dev copy and tested against one throwaway appointment, then a rollout plan: snapshot, swap, prompt change and gateway restart as separate steps, then an end to end check.

Knowledge base agentMF-06 KB · OpenClaw on Telegram, backed by Supabase

Status. Personal build.

10.1Overview

A Telegram agent on OpenClaw that learns from documents kept in Supabase. Before connecting, it asked the questions that decide the design: where documents live, whether to use the service role key or the anon key with row level security, and whether documents belong to one user or are shared.

Telegram caps file uploads, so documents go straight into a Supabase Storage bucket instead. The agent fetches each file, extracts the text, writes it into the knowledge base, and answers from it with the source named. The test corpus was security material: a 31 MB Windows Server identity PDF and MIT's Kerberos documentation.
