Funnel Studio: AI Funnel Builder for a Live Event

5 October 2026

What it is

Funnel Studio is a web app where someone scans a QR code, chats with an AI agent for a few minutes, and walks away with a finished landing page for their business. It was built for a live event where more than 100 guests would do this at the same time, on the same venue Wi-Fi, each getting their own private workspace.

The final load test: 100 of 100 guests got a page in 14 minutes, nobody was turned away, no reply failed, and the whole room cost about $5.80 in model usage on a two-core server.

The guest sees a chat and a live preview side by side. Behind it sit a React app on Netlify, a Node bridge that owns the queue and the files, and a Hermes AI agent running a purpose-built skill, with a safety plugin that keeps every guest locked inside their own folder. It runs today as two independent deployments, a primary and an identical backup on a separate server, so the event has a spare.

How it works

The guest's browser only ever talks to two hostnames, both served by Traefik: the bridge's API and the preview host. The bridge holds everything stateful, the queue, the database, the guests' files, and the agent container is reachable only over the private Docker network, never from the internet. Each funnel gets its own agent session and its own folder, and the bridge writes a short note into every turn telling the agent the guest's name, which style to use, what has been uploaded and whether the page exists yet.

The web app is static and deploys separately from the server, so a UI change never touches the queue, and the API refuses any origin but its own site.

The guest journey

From scanning the code to a finished page takes about four short answers and two minutes of waiting. Every screenshot below is the live system, captured on the backup deployment.

1. Scan and join. The QR code opens the app. There is no account, no password and no email: the name is optional and the device gets its own private space. One organiser password controls the codes behind the scenes.

2. Four questions, one at a time. The agent greets them by name and asks what the business is, what visitors should do and what the button should say, what the page is for and whether there is an offer, then how it should look. Each answer comes back in a few seconds. A guest in a hurry can fill a short brief form instead and skip straight to the build.

3. It builds while they watch. The agent picks a style, writes the whole page as one self-contained HTML file, runs its own checker over it, and fixes anything that fails before saying it is ready. The preview beside the chat refreshes the moment the file is saved, and the small ticks above the chat show what the agent is doing.

4. The page, and what they can do with it. Guests ask for changes in plain language ("make the headline shorter", "try something bolder"), and every change is saved as a version they can roll back to. Above the preview they get a share link and a download, as HTML or a ZIP with the images.

This one took four answers: a neighbourhood bakery doing sourdough and celebration cakes, an Order My Cake button, filling quiet weekday afternoons with 10% off a first order, and a warm and friendly look. Everything else, including the brand name, the copy, the section order and the colour palette, the agent chose.

Keeping a hundred strangers apart

The agent has file tools and internet access, and a hundred strangers are pointing it at their own folder, so the isolation is enforced in code rather than asked for in the prompt. A plugin sits in front of every tool call the agent makes and decides before it runs.

RuleHow it is enforced
One folder per funnelThe plugin works out the folder from the session name and rewrites every relative path into it. An absolute path, a .., a symlink or another guest's folder is refused.
Only the tools this job needsAn allowlist: file tools, the skill reader, web search and fetch, the page checker. Shell, code execution, process control, the browser, memory, session search, cron and delegation are all blocked.
Images only from the guestThe downloader is refused outright, the page checker treats any image loaded from elsewhere as an error, and the site fetcher deliberately returns no pictures.
No cross-session memoryMemory is switched off for this profile, because a profile's memory is shared by every guest in it.
Fails closedIf the check times out, the tool call is blocked rather than allowed.

The guard is covered by 61 tests that run before any install, including attempts to escape the folder, reach the server's own dashboard, read the environment file and fetch internal addresses.

Two more boundaries sit outside the agent. The web agent runs as its own profile inside the AI container with its own API key, so a guest's conversation can never reach the owner's personal assistant on the same machine. And the preview is served by the bridge from the guest's folder on a separate hostname, so a page can be shared without exposing the app or the API.

Making every page look different

Early testers noticed that every funnel came out looking the same. The page template hard-coded one look, the design guide offered four presets that mostly shared a palette, and nothing in the conversation ever asked how the page should look.

The fix was a style library and a pick the agent is not allowed to override:

  • Seven moods, chosen from the kind of business, not from the words the guest used: warm and friendly, bright and playful, clean and minimal, dark and premium, bold and energetic, natural and calm, classic and trustworthy. A bold voice for an AI agency still gets a dark, premium page.
  • Four styles inside each mood, each with its own page colour, fonts and hero treatment, so two cafés in the same mood do not get the same page.
  • A variety pick (A to D) derived from the funnel's own id, handed to the agent in a note on every turn. It picks the style with that letter even if another one sounds like a better fit, which is what keeps a room full of pages apart.
  • A structure-only template. The scaffold carries no look of its own; the style supplies the fonts, the colour tokens and the section rhythm.

In the hundred-guest runs the result was 24 to 28 distinct page styles per run. The model also kept trying to talk itself out of the pick, which is why the per-turn note is binding and the "best for" hints were removed from the style files: with them in place, the agent reasoned its way back to the same favourite.

Surviving 100 people at once

A harness played 100 scripted guests through the public API exactly as the web app does: join with the QR code, start a funnel, chat over the live stream, load the preview, and about half ask for one change afterwards. They arrive the way a room scans a code that just went up on screen, most within the first three minutes. Every run uses the same 100 businesses, the same arrival times and the same random seed, so runs can be compared.

The first run was the useful one, because it showed the server was never the problem. CPU peaked at 52% and memory never dropped below 2.6 GB free, yet 32 of the 100 guests were turned away with "very busy", and a question the agent answers in three seconds waited six minutes in line behind page builds.

Five fixes followed, each aimed at something the measurement showed:

  1. Joining allowed 12 people a minute per connection. A room on one Wi-Fi would mostly have seen "too many attempts". Raised to 200 a minute: the 100 test guests joined in 40 seconds instead of 9 minutes.
  2. The line held 60 messages. While it was full, guests were refused. Raised to 300, and nobody has been turned away since.
  3. Quick replies queued behind page builds. A chat answer takes seconds, a build takes a minute. Intake messages now skip ahead in their own lane, while the message that starts a build waits its turn, so builds can never be starved.
  4. The app said "the agent will start in a moment" even at 38th in line. It now shows a real estimate, worked out from the work queued in front of each message rather than from the position alone.
  5. The intake cost four trips through the line. It was condensed, and later restructured into the four-questions-one-at-a-time flow once capacity allowed it.

One fix backfired and the measurement caught it. The first version of the fast lane promoted anything that had waited four minutes, which at the busiest moment promoted everything, so the lane stopped existing and the worst quick reply took 14 minutes. The owner also saw their own place in line climb from 35 to 46 while testing. Removing the promotion rule fixed it: quick replies are about one per guest and take seconds, so they cannot starve the builds behind them.

The ceiling nobody could see

After the queue fixes, nobody was turned away but the room still took 32 minutes, because pages were built four at a time. Raising that number had been tried once and barely helped, and the reason turned out to be two levels below the app.

The AI runtime runs each agent turn on a thread pool it sizes from the processor count, cores + 4. On a one-core server that is five threads, whatever the app's own limit says. Setting the app to 10 simply queued the extra turns invisibly inside the runtime, where the app's queue, its wait estimates and its fast lane could not see them: a three-second question took 21 seconds, and at the arrival peak four guests could not start a funnel at all.

The fix was a server with two cores, and telling the runtime it has ten so the pool holds 14 threads: ten for guests, two for the owner's own assistant on the same machine, and two so short housekeeping work never waits behind a 90-second page build. Threads are created on demand, so unused headroom costs nothing, while a missing thread costs invisible queueing.

In both runs at this setting the model provider started refusing requests in short bursts, the first time that had happened. The agent retried through every one and no guest saw a failure, but that rate limit, not the hardware, is now the first thing that would bend under a bigger room.

A second deployment, as the spare

An event with one server has one way to fail, so the whole stack was rebuilt on a second server with its own agent, its own Telegram bot, its own model key, its own database and its own Netlify site. Guests on one never touch the other.

The copy had to be exact where it mattered and different where it mattered. Every host-specific value was swapped in one commit: container and network names, data paths, API and preview hostnames, the site name, the server address. That included both copies of the web app's content security policy, which pin the API and preview hostnames. Missing those would have produced a site that looks perfect and is silently blocked from calling its own API by the browser.

The skills, the plugin, the profile config and the persona were then checked file by file against the live primary: 137 files, every one identical except a single line in a test that names the local container.

Four traps surfaced because the new server shipped a newer build of the AI runtime:

  1. A script that reported success and did nothing. It skipped its edit if the multiplexing key appeared at all, and the newer build ships that key already present, set to false.
  2. A safety check that could never pass. It validated using an argument the new version had removed, so it would have rolled itself back every time.
  3. A missing model key. The installer copied the key with a grep on an environment file. On this server the key had been added through the dashboard, so it lives in the credential store, the grep matched nothing, and the script aborted halfway.
  4. A removed allowlist. The newer version serves every named profile when multiplexing, instead of a named list, so the verification now asserts that only the intended profile exists and only it is served.

One trap had nothing to do with versions and would have been the expensive one: the deploy script trusts a cached site id before looking the site up by name. Copying that file across with the credentials would have pointed every deploy from the new server at the primary's live site. Only the token was copied, and the script now ignores a cached id unless the name matches.

Running it

Every change to the live system goes out the same way: a restore point first, then the change, then a verification that can refuse it.

  • A restore point before every change. A git tag, the previous container image tagged, the live site's deploy id, a copy of the agent's skills and plugin, and a notes file with the exact rollback commands. Rolling back is a handful of commands, not a reconstruction.
  • Deployments that test themselves. The bridge image only builds if its unit tests pass. The plugin installer stages a copy inside the container, runs the plugin's 61 tests against the staged copy, and only swaps it in if they pass, so a broken plugin can never reach the live path and take the safety guard with it.
  • Checks that run after, not just before. After any restart: the profile isolation checks, the guard tests, and a real guest building a real page through the public API.
  • Firewall. Only 22, 80 and 443 are open, and enabling it arms a five-minute dead-man timer that switches it back off if the checks fail, so a firewall change cannot lock anyone out. The AI dashboard's container port is blocked by a rule that survives reboots and port changes, leaving it reachable only over HTTPS.
  • Backups. A nightly job snapshots both databases with the online-backup API so the archive is consistent while the services run, plus the guests' pages, the profile and the deploy code, keeping the last seven. Secrets are deliberately excluded.
  • A reboot test. The backup server was rebooted on purpose: containers, firewall rules, the queue, certificates and the backup timer all came back by themselves in about 40 seconds, and a guest built a page immediately after.

Two bugs in this area were found only because a fresh server was built. The nightly backup failed on a brand new install, because it archives a folder the bridge only creates once a first page is saved. And the firewall rule had to match the dashboard's container port rather than its published one, because the published port changes every time the container restarts.
